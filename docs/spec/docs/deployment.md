# Развёртывание

## Исходная инфраструктура

По сведениям владельца:
VPS KVM SSD Cuprum, 2 CPU, 2 GB RAM, 30 GB SSD, EU,
финский IP. На сервере уже работает изолированный Hermes.

Не считать это гарантией достаточных ресурсов и не считать IP доказательством
фактической юрисдикции всех обработчиков.

## Предварительная проверка

Получить разрешение владельца, затем read-only проверить:
ОС, поддержку PostgreSQL 16 и pgvector, свободную память и swap, диски и inode, процессы,
потребление Hermes, занятые порты, существующий proxy, backups, firewall.

Не менять чужие сервисы.
Сохранить текущие конфигурации перед любым согласованным изменением.

## Изоляция

Отдельные Unix user, каталог проекта, venv, systemd units,
DB role и database. API-ключи доступны только сервису.
Пользователь сайта не имеет прав на Hermes, Docker socket и sudo.
Приватные файлы хранятся вне static; выдача только после проверки владельца.
Egress для worker ограничивается необходимыми API и разрешённым согласованным
получением документов; доступ к loopback/private networks запрещён и приложением,
и, где возможно, сетевой политикой.

Gunicorn слушает loopback.
PostgreSQL не публикуется в интернет.
Использовать существующий proxy; не запускать второй на том же порту.

## Начальный профиль

Один Gunicorn worker с небольшим числом threads,
один AI-worker, ограниченные DB connections.
Это начальный профиль для проверки, не обещанный capacity.

Конкретные MemoryHigh/MemoryMax задаются после измерений.
Сайт и Hermes должны иметь согласованный общий запас памяти.
Не «лечить» нехватку RAM только увеличением swap и отключением ограничений.

## Последовательность

1. Утвердить размещение данных.
2. Выделить ресурсы и сервисного пользователя.
3. Установить зависимости из lock.
4. Создать DB и секреты.
5. Сделать backup перед миграциями существующих данных.
6. Выполнить migrate и collectstatic.
7. Загрузить начальные материалы.
8. Настроить web, worker и maintenance timer.
9. Настроить proxy, HTTPS и firewall.
10. Выполнить deployment check и smoke сценарии.
11. Только затем открыть регистрацию и живой ИИ.

Не запускать Django runserver как production сервер.

## Развёртывание кода

Сначала локально и через частный репозиторий.
Сборку CSS/JS, если она нужна, выполнять локально/в CI.
Не тратить ресурсы малого VPS на тяжёлую сборку frontend.

## Откат

Хранить предыдущий release и lock.
Разделять обратимые изменения кода и необратимые миграции.
При несовместимой миграции — maintenance, backup и проверенный план возврата,
а не простое переключение Git commit.

## Резервные копии

Ежедневная зашифрованная копия базы и необходимого контента.
Хотя бы одна копия вне этого VPS.
Ротация default 14 дней, ограничение места и мониторинг ошибок.

До публичного запуска восстановить копию в отдельную базу и проверить вход,
тексты, документы/chunks/embeddings, evidence, кредитный ledger и журнал удалений:
ранее удалённые аккаунты и документы не должны вернуться после восстановления.
В backup входят необходимые приватные файлы и версии источников, а не только PostgreSQL.
Для pgvector проверяются доступность расширения, права DB role и восстановление индексов.
