# HTTP-контракты и фоновые задачи

## Общие правила

Session auth и CSRF для браузера.
GET не изменяет данные. Все ID сверяются с владельцем или публичным статусом.
Ответы ошибок: code, безопасное message, request_id.
Не раскрывать существование чужого проекта: 404.

## Создание AIJob

Тело:
Для AIJob: kind = generate / edit_series / edit_part / edit_sentence / ask,
base_revision_id, target_id nullable, document_ids, instruction,
idempotency_key, expected_head_revision_id.
Для import_source/index_source/search_sources используются отдельные операции с
idempotency_key и соответствующими document/selection параметрами. Загрузка файла
создаёт документ и import_source; повторная индексация создаёт index_source.
document_ids должны принадлежать владельцу или входить в разрешённый редакционный
корпус; для simplify_source первичный документ задаётся отдельным полем.

Модель, цена, retrieval scope, URL для fetch, системные сообщения, citations и
текст замены как JSON Patch из браузера не принимаются. Выбор search result —
это выбор кандидата, а не разрешение обойти проверки fetch и прав.

Ответы:
202 — задача принята;
200 — повтор существующей задачи;
402 + code insufficient_credits — нужен баланс;
409 — несовпадающий payload с тем же ключом или конфликт ревизии;
429 — частотный лимит;
503 — бюджет/провайдер/конфигурация недоступны.

402 здесь — внутренний HTTP-контракт, не свидетельство подключённой оплаты.

## Принятие задачи

В одной транзакции:
проверить права и ограничения, проверить idempotency,
заблокировать wallet, проверить доступный остаток,
зарезервировать кредиты и денежный максимум,
создать задачу и запись пользовательской инструкции.
Для бесплатных import/index/search wallet-резерв не создаётся, но остаются денежный
лимит, квота, idempotency и защита от неопределённых повторов.

Порядок блокировок единый:
wallet → бюджетные buckets в фиксированном порядке → project/job.
Сетевых операций в транзакции нет.

Повтор ключа с тем же payload возвращает исходную задачу даже после завершения.
Другой payload с тем же ключом отклоняется.
Явное «попробовать снова» создаёт новый ключ.

## Состояния

queued → running → succeeded
queued → cancelled
running → failed
running → reconciliation_required → succeeded/failed

stage: prepare, extract, index, search, fetch, retrieve, generate, answer, review,
repair, finalize. Внешние операции регистрируются отдельными попытками.
queued → running для import/search/index также допустимы; платный AI-результат
фиксируется через outcome. needs_clarification/refused/needs_broader_edit —
доставленный no-charge outcome, не paid success.
Состояние reconciliation_required означает неопределённый внешний исход,
а не разрешение повторно отправить запрос.

## Выполнение и завершение

Worker захватывает задачу короткой транзакцией.
Перед отправкой сохраняет ProviderAttempt и request_hash.
После ответа фиксирует provider ID, usage, стоимость и checkpoint.

Доставка платного outcome=delivered: валидный результат, сообщение/ревизия,
окончательное списание, освобождение кредитного резерва и статус succeeded —
одна транзакция. Для needs_clarification/refused/needs_broader_edit и бесплатных
import/index/search сохраняется полезный результат или статус, резерв освобождается
без debit, а задача завершается succeeded с соответствующим outcome.
no_charge_failure используется при неуспехе с уже доставленным бесплатным объяснением;
необработанная техническая ошибка остаётся status=failed.

Job success означает завершение обработки и надёжную доступность результата в кабинете,
а не обязательное списание или успешную генерацию текста.
Закрытый браузер не отменяет успешное выполненное действие.

## Сбои и отмена

Queued можно отменить с освобождением резервов.
После отправки внешнего запроса отмена не обещается.

Timeout после отправки: не повторять автоматически.
Попытаться сверить по provider ID, если он известен.
Через 15 минут без доставляемого результата завершить пользовательскую задачу
неудачей и освободить пользовательские кредиты.
Неопределённый денежный расход владельца оставить зарезервированным до сверки.

Поздний результат после такого завершения не списывает кредиты.
Зависшие резервы контролируются maintenance и аудитом.
